# Requirements

## Problem

Any product that emits webhooks has to solve the same set of problems: retrying failed
deliveries, signing payloads so receivers can trust them, letting operators inspect and
replay what went wrong, and not hammering endpoints that are down. Most teams solve this
ad hoc, inside their main application, and the result is lost events, duplicated events,
and no visibility.

Carteiro is a self-hostable service that takes over that responsibility. A producer
system sends an event to Carteiro once; Carteiro fans it out to every subscribed
endpoint, signs it, retries it, records every attempt, and exposes the state of every
delivery through an API.

## Actors

| Actor | Description |
|---|---|
| **Operator** | Runs the Carteiro instance. Creates applications and API keys using the admin token. |
| **Producer** | A system (e.g. a SaaS backend) that publishes events through the API using an application API key. |
| **Receiver** | An HTTP endpoint, owned by the producer's customer, that receives signed webhooks. |

## Functional requirements

### Applications and authentication
- **FR-01** The operator can create applications using a static admin token.
- **FR-02** The operator can issue and revoke API keys per application. A key is shown
  only once at creation; Carteiro stores only its hash.
- **FR-03** Every application-scoped request is authenticated with `Authorization: Bearer <api key>`
  and can only see resources of its own application.

### Endpoints
- **FR-04** A producer can create, list, update, and delete endpoints (URL, description,
  optional list of event types to subscribe to; empty list means all types).
- **FR-05** Each endpoint has a signing secret generated by Carteiro, returned on creation.
- **FR-06** A producer can rotate an endpoint secret. The previous secret remains valid
  for a configurable grace period (default 24 h), during which deliveries are signed with
  both secrets.
- **FR-07** Endpoint URLs are validated on creation: must be absolute, `https` (plain `http`
  only when explicitly allowed by configuration), and must not resolve to a blocked
  network range (see NFR-SEC-03).
- **FR-08** An endpoint is disabled automatically after failing continuously for a
  configurable period (default: 5 days with no successful delivery, and at least 10
  consecutive failures). A `410 Gone` response disables it immediately.
- **FR-09** A producer can re-enable a disabled endpoint.

### Events and delivery
- **FR-10** A producer can publish an event (`event_type`, JSON `payload`) with an optional
  `Idempotency-Key` header.
- **FR-11** Publishing with an `Idempotency-Key` already used by the same application
  returns the original event (`200`) if the payload is identical, or `409 Conflict` if it
  differs. A new event returns `202 Accepted`.
- **FR-12** Publishing an event atomically creates one delivery for every active endpoint
  subscribed to its type (fan-out at ingest).
- **FR-13** Each delivery is sent as an HTTP `POST` with a JSON body, signed according to
  the [Standard Webhooks](https://www.standardwebhooks.com/) specification
  (`webhook-id`, `webhook-timestamp`, `webhook-signature` headers).
- **FR-14** A delivery succeeds on any `2xx` response. Any other outcome (non-`2xx`,
  timeout, connection error) schedules a retry with exponential backoff and jitter.
  `Retry-After` on `429`/`503` is honored, capped by the maximum backoff.
- **FR-15** After the maximum number of attempts (default 12), a delivery is marked `dead`.
- **FR-16** Every attempt is recorded: timestamp, duration, response status, the first
  4 KiB of the response body, and the error, if any.
- **FR-17** A producer can query an event, its deliveries, and each delivery's attempts.
- **FR-18** A producer can replay a single delivery, or every `dead` delivery of an
  endpoint since a given timestamp.

### Operations
- **FR-19** `GET /healthz` (process is alive) and `GET /readyz` (database reachable).
- **FR-20** `GET /metrics` in Prometheus format: deliveries by outcome, delivery latency,
  queue depth, and age of the oldest pending delivery.
- **FR-21** Events and attempts older than a configurable retention period are purged.

## Non-functional requirements

### Reliability
- **NFR-REL-01** Delivery is **at-least-once**. An accepted event is never lost, even if a
  worker crashes mid-delivery. Duplicates are possible and receivers deduplicate using
  `webhook-id`.
- **NFR-REL-02** Ordering between events is **not** guaranteed.
- **NFR-REL-03** No database transaction is held open across a network call to a receiver.
- **NFR-REL-04** API and workers shut down gracefully: in-flight requests and deliveries
  finish (bounded by a timeout) before the process exits.
- **NFR-REL-05** Multiple worker processes can run concurrently against the same database
  without coordinating with each other.

### Security
- **NFR-SEC-01** API keys are random (≥ 256 bits) and stored as SHA-256 hashes.
- **NFR-SEC-02** Endpoint secrets are encrypted at rest with AES-256-GCM using a key
  provided via environment variable.
- **NFR-SEC-03** Outbound requests cannot reach loopback, private, link-local (including
  cloud metadata at `169.254.169.254`), CGNAT, or multicast addresses. The check happens
  at connection time, so DNS rebinding cannot bypass it.
- **NFR-SEC-04** Redirects from receivers are not followed.
- **NFR-SEC-05** Request bodies are size-limited (default 256 KiB payload).
- **NFR-SEC-06** Secrets and API keys never appear in logs.

### Performance (targets, to be measured and published)
- **NFR-PERF-01** Ingest p99 latency below 50 ms on a developer laptop.
- **NFR-PERF-02** At least 500 deliveries/s with 4 workers against a fast local receiver.
- **NFR-PERF-03** Throughput scales roughly linearly when adding workers, until the
  database becomes the bottleneck. The bottleneck is identified and documented.

### Maintainability
- **NFR-MNT-01** Every feature has automated tests. Database code is tested against a real
  PostgreSQL instance, not mocks.
- **NFR-MNT-02** CI runs lint, tests (with the race detector), and builds the container
  image on every pull request.
- **NFR-MNT-03** The whole stack runs locally with one command (`docker compose up`).
- **NFR-MNT-04** Significant decisions are recorded as ADRs in `docs/adr`.

## Out of scope

These are deliberate non-goals, documented so the scope stays honest:

- Exactly-once delivery or ordering guarantees.
- A customer-facing portal for the producer's own customers.
- Multi-region deployment, billing, or user accounts beyond the admin token.
- Transformations of payloads, or protocols other than HTTP.
